# テストレビュー

不足だけでなく、目的に対して不要・過剰なテストもレビューする。

## テストの価値と負担

恒久的な回帰テストとして残すべき保証と、今回の導入・変更が動くことを確かめる一度限りの実行確認を分ける。
プロジェクト固有の挙動・安全要件・既知の不具合の再発を守る必要があるかを基準に、次を比較する。

- どの条件・失敗を検知し、どの要件や回帰を守るか。外部ツールの標準動作を再確認するだけで、プロジェクト固有の保証を加えていないか。
- 既存テストと条件・失敗の検知範囲が重複していないか。別の層や経路で確認することに独自の価値があるか。
- 得られる保証に対し、実行時間、準備の負担、メンテナンスコスト、モック・専用基盤、不安定さへの対処の負担が見合うか。負担は確認できる実装や実行記録を根拠にし、計測していない数値を推測で補わない。

外部ツールを使うだけで不要とはしない。プロジェクトの設定・接続・組合せに起因する失敗や安全要件を守る統合テストには、恒久的に残す価値がある。
安全上の保証を、重複や負担だけを理由に失わない。

追加・維持・統合・削除・一度限りの実行確認への置換は、対象箇所と守る保証、既存テストとの差、負担を根拠に最小案を示す。
削除・統合・置換を提案する場合は、失われる保証の有無と残す検証で十分な理由を示す。根拠が不足する場合は不要と断定しない。
一度限りの実行確認を提案する場合も、何をどう確認するかを具体化する。これは必要な CI・E2E 等の品質条件を免除する判断ではない。

## テストの妥当性

- 変更された挙動・要件に対応するテストがあるか
- 異常系・境界値・回帰が押さえられているか
- テストが実際に失敗しうるか(常に通る検証、過剰なモック、アサーション不足)
- 不安定さの要因(時刻、順序、外部依存、共有状態)
- 適用規約のうちテストに関わるもの
- AAA(Arrange・Act・Assert)で準備・実行・検証が区別され、形式のためだけに不要な複雑さを増やしていないか

レビュー担当は報告のみで、テストの追加・変更・削除や検証の実行は行わない。
テストを実行したかのように書かない。実行していなければ、読んで判断した旨を明記する。
